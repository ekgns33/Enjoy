# 자료구조와 OS 캐시

* 캐시 이전에 알아야할 CS 개념 : 탐색, 해시

프로그램을 작성하다보면 값을 디스크나 메모리에서 읽어오고, 값을 조작하여 다시 저장하는 일이 전부인 경우가 많다. 프로그램의 로직 뿐만아니라 컴퓨터 시스템에서 값을 저장하고 조회하는 것은 cpu부터 시작하여 모든 시스템에서 사용된다.

* **선형 탐색**

덤프로부터 데이터를 읽어서 메모리의 자료구조에 저장할때, 그냥 리스트에 저장했다고 생각해보자. 특정 원소를 찾기 위해서는 전체 자료구조를 확인해야한다. 따라서 $$O(n)$$의 시간 복잡도가 소요된다.

* **이진 탐색** 만약 데이터가 숫자라면 이야기가 조금 달라진다. 데이터를 저장할때, 정렬이 유지되는 자료구조를 사용한다면 삽입, 조회, 삭제를 $$O(logn)$$ 에 수행할 수 있다. 물론 이는 Balanced Binary Tree 자료구조를 사용할때 이야기이다.

* **해시** 우리가 마주하는 데이터들은 보통 문자열이나 복잡한 객체이다. 이 친구들이 자신만을 의미하는 고유한 값들이 있다면 우리는 $$O(1)$$ 에 값을 조회할 수도 있다.

하지만 보통 자료구조들은 $$O(logn)$$ 의 시간복잡도가 사용된다. Java의 경우 자료구조의 크기가 커지면 List에서 레드블랙트리로 변경된다.



알고리즘 문제들을 풀다보면 문제가 요구하는 시간복잡도를 맞추기위해 일반적인 collection 자료구조를 사용하지 않는 경우도 많다.

* 문자열의 길이가 작다면 비트로 문자열을 치환하여 상수 시간에 접근할 수 있다.
* 숫자 시퀀스가 들어왔을때, 숫자들의 차이를 사용하여 해시를 만들 수도 있다.

```kotlin

// 문자열의 길이가 작은경우 + 알파벳만 있다면 다음과 같이 직접 해시할수도 있다.
// 하지만 숫자 범위에 유의해야한다. 27진수로 표현가능한 범위까지만 사용가능하다.
fun encodeStringWithBits(String s) {
    var isEnd = false
    var hash: Long = 0L
    val n = s.length()
    for(let i in 0..n) {
        hash *= 27
        hash += (s.charAt(i) - 'a' + 1)
    }
    return hash
}

```

**결국 시간복잡도를 어떻게든 줄이기 위한 노력들이다.**

***

우리가 설계하는 시스템으로 시야를 확장해보자.

* 사용자의 요청에 따라 비즈니스로직을 처리하는 서버 애플리케이션을 개발하고있다.
* 데이터들은 데이터베이스에 저장되어있고, 우리는 이를 조회하여 가공하고 반환해야한다.

**저장과 조회**

데이터베이스에 저장할때, 인덱스를 제대로 걸었는지 확인한다. 인덱스 없이 select를 수행하면, 테이블 풀스캔을 할 확률이 높아진다. 하나의 데이터를 조회했는데, 전체 데이터를 돌면서 조건문을 수행하는 방식은 Linear-Search에 가깝다.

* Binary-Search로 나아갈 수 있을까?

데이터베이스들은 B-Tree / B+Tree구조를 채택하는 경우가 많다. 데이터베이스는 결국 File을 저장하는 시스템이고 얼마나 최적으로(잘) 데이터를 조회/수정할지가 중요하다. 탐색에 사용되는 자료구조는 보통 트리가 선택되는데 그 중에서도 **B트리는 하드디스크상에 구축하기 좋은 자료구조이므로 사용된다.**

> B트리와 B+트리가 하드디스크상에서 사용하기 좋은 구조인 이유는, 디스크 READ의 동작 방식과, OS 캐시등을 이해해야한다!

* 인덱스까지 활용하여 우리는 $$O(logn)$$의 시간복잡도로 데이터를 조회할 수 있게되었다.

**더 빠르게?**

더 빠른게 뭐가 있을까? 데이터베이스에서 $$O(1)$$을 만들 수는 없다. 알고리즘 문제를 풀때, 자주 사용하던 방법을 떠올리자.

* **자주 사용하는 것들은 따로 저장해 놓기**

운영체제를 공부할때, 운영체제는 **디스크로부터 데이터를 읽어와서 바로 휘발시키지 않는다**는 것을 배웠다. 페이지캐시로 메모리에 올려두고 수정이 일어나면 캐시에 업데이트를 한다. 이것은 스케줄러에 의해 디스크에 플러시된다.

알고리즘 문제를 풀때도, **수정된 부분은 Lazy하게 업데이트**하는 방법이 있다. 또한 수정되지 않은 부분은 아예 업데이트 범위에 포함하지 않는다.



**CS에서 보통 이런 것을 캐시(Cache)라고 부른다.**

* 캐시는 단순 메모리에서만 사용하는 게아니라 CPU에서도 사용한다. CPU에는 실제로 L1, L2 캐시가 있고 캐시 정책또한 정해져있다.&#x20;
* 운영체제에서는 페이지캐시나 swap 공간에 대한 eviction 정책이 구현되어 있기도하다.



우리는 간단한 정책으로 이 캐시를 활용한다.

* 데이터베이스에 누군가 조회를 하면 그 데이터를 메모리에 저장해놓는다.
* 데이터가 수정되면 저장해놓았던 데이터도 업데이트한다.

이를 통해 **데이터베이스에 직접 쿼리를 날리지 않아도** 메모리에 저장되어있던, 데이터를 반환해줄 수 있다. 캐시의 key는 쿼리가 될수도 있고 조회하려는 객체의 고유id일 수도 있다.

**OS 캐시**

운영체제에서 페이지 캐시, 버퍼캐시를 배운적 있다.

페이지 캐시는 Java NIO를 공부할때도 나왔던 개념인데 다시 한번 짚고 넘어가자.

* **페이지(Page) 캐시**

가상 메모리 구조에서 운영체제는 논리적인 선형 메모리 주소를 물리 주소로 변환한다.

메모리 가상화를 위해 주소 변환은 꼭 필요하다. 가상 메모리를 통해 유저 프로그램이 커널의 실제 메모리 주소에 직접 접근하는 것을 막고, 효율적인 사용을 이끈다.

프로그램에서 메모리에 접근해야할때도 **운영체제는 정확히 요구하는 크기만 제공하는게 아니라 페이지 크기 단위로 메모리에서 가져와 제공한다.** 제공한 페이지는 다시 사용될 확률이 높기에 캐시에 저장하게된다. 페이지의 단위는 보통 4kb로 알려져있다.

흐름을 정리하면 이렇다.

1. 디스크로부터 페이지 크기만큼 블록을 읽어온다.
2. 가상 메모리에 쓰기를 진행한다
3. 가상메모리의 주소를 프로세스에 알려준다.
4. 프로세스는 메모리에 액세스한다.
5. 바로 페이지를 해제하지 않고 유지시킨다. (이를 통해 프로그램은 DISK IO가 아닌 메모리에서 데이터를 읽는다.)
