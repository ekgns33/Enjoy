## HTTP/2.0

HTTP/1.1에서는 병렬 커넥션과 파이프라인 커넥션이 도입되었다. 하지만 구현의 단순성과 접근성에 주안점을 두고 최적화 되었다고 한다.

성능을 개선하기 위해 구글에서 2009년 SPDY라는 프로토콜을 개발했다.

* 헤더를 압축하여 대역폭을 절약
* 하나의 TCP 커넥션에 여러 요청을 동시에 보내 RTT를 줄임
* 클라이언트의 요청 없이도 서버가 리소스를 푸시



모두 RTT를 줄이기 위한 작업이다. SPDY를 적용하여 구글은 실제로 RTT가 20ms일때 12.34%, 80ms일때 23.85%의 성능 개선을 이뤄냈다고한다.

이를 기반으로 HTTP/2.0 프로토콜이 설계되었다. SPDY와 크게 다른 점은 헤더를 압축할때 deflate 알고리즘을 사용하지 않는다는 것이다.

***

* **Deflate 알고리즘?**



위키 백과 - 헤더압축 : https://ko.wikipedia.org/wiki/HTTP\_%EC%95%95%EC%B6%95

> DEFLATE는 기본적으로 [LZ77](https://ko.wikipedia.org/w/index.php?title=LZ77\&action=edit\&redlink=1) 알고리즘을 통해 데이터를 압축한 뒤, 중복되는 내용에 대한 포인터(일치하는 내용의 위치와 길이)를 [허프만 부호화](https://ko.wikipedia.org/wiki/%ED%97%88%ED%94%84%EB%A7%8C_%EB%B6%80%ED%98%B8%ED%99%94)를 사용하여 한 번 더 압축한다.\
> DEFLATE 알고리즘은 일반적으로 그 압축률에 비해 압축/해제 속도가 빠르나, 나중에 나온 압축 알고리즘에 비해서는 압축률이 다소 떨어지는 경향이 있다.

* 웹 브라우저 상에서 압축을 한다면 gzip이나 deflate을 주로 사용한다.
* 여러가지 보안 이슈가 있어서 HTTP/2.0은 deflate를 제외한 것 같다. 압축 알고리즘을 상용 소프트웨어들이 지원하는 지 여부도 영향을 준 것 같다.

### Frame

HTTP/2.0은 TCP 커넥션에서 동작한다. 이때 커넥션은 클라이언트가 초기화 한다.



**HTTP/2.0의 요청과 응답은 길이가 정의된 한 개 이상의 프레임(frame)에 담긴다. 헤더는 압축된다.**

* 프레임에 담긴 요청과 응답은 스트림으로 보내지는데, 한 개의 스트림이 한 쌍의 요청과 응답을 처리한다.
* 커넥션위에 여러 스트림이 동시에 만들어질 수 있기 때문에, 여러 요청과 응답을 처리하는 게 가능해진다.
* HTTP/2.0은 스트림에 대한 흐름제어와 우선순위 부여도 가능하다.



**재밌는 것은 이렇게 프레임을 쪼개는 것이 기존의 HOL문제를 해결하는 것이다.**

HTTP/1.1은 FCFS로 요청을 처리한다. 따라서 HOL이 발생했다.

### Stream

**스트림은 HTTP/2.0 커넥션을 통해 클라이언트와 서버 사이에서 교환되는 프레임들의 독립된 양방향 시퀀스이**\
**다.**

스트림이라는 단어가 IT업계에서 상당히 자주나온다. I/O 처리에 있는 Stream, HTTP의 Stream, 람다의 Stream, ... 심지어 레디스 Stream도 있다.

* 여기에서는 데이터의 흐름을 이야기하는 것 같다. (커넥션의 연결성)

HTTP/1.1에서는 위에서 언급했듯이 한 커넥션으로 요청을 보낼때, 응답이 도착해야 다음 요청을 보낼 수 있었다.\
따라서 브라우저는 성능을 올리기 위해 병렬 커넥션을 만들어 사용했다.



**그렇다고 무한히 커넥션을 만들어?**

현대 웹서비스들은 수십 수백개의 요청을 날린다. 이걸 다 커넥션을 수립하기에는 무리가 있다. 파이프라인 커넥션이라는 해결책이 있기도하다. (구현된게 얼마 없는듯)



**하나의 커넥션에 여러 스트림을 열어버려**

HTTP/2.0에서는 한 커넥션에 대해 여러 스트림을 열 수 있다. 또한 스트림이 우선순위를 가질 수도 있다. 헤더에 비트값에 우선순위를 표시하여 더 중요한 리소스를 표시할 수 있다.

* but 우선순위 표시한다고 그게 먼저 처리되는 것은 아님.

***

### Stream에 대한 더 많은 이야기들

**서버와 클라이언트는 상대와 협상없이 스트림을 만든다. 협상을 위해 패킷을 주고받는 시간낭비를 줄이는 것이다.**

* 이미 커넥션을 맺을때 핸드셰이크를 마쳤는데 굳이 스트림을 만들때 또 협상할 이유가 없어보인다.



**한번 사용한 스트림 식별자는 다시 사용할 수 없다.**

* 각 스트림은 식별자를 갖는데, 스트림을 게시한 주체에 따라 홀수 짝수가 나눠진다.
* 서버는 짝수, 클라이언트는 홀수이다.

모든 식별자를 다 써버리면 커넥션을 다시 맺는다.



**스트림이 많아지면 블로킹 문제가 생길 수 있지 않을까?**

* HTTP/2.0은 WINDOW\_UPDATE 프레임을 사용해 흐름제어를 달성한다.
* 서로 간섭하는 것을 막는다.

### Header

HTTP/1.1에서는 헤더가 아무런 압축 없이 전송되었다. 요청이 적을때는 헤더의 크기가 문제가 되지 않았지만, 웹페이지에 수많은 요청들이 늘어나며 헤더의 크기는 대역폭에 큰 영향을 주었다.

* RTT + Bandwidth에 영향!



HTTP/2.0에서는 헤더를 압축하여 전송한다. HPACK이라는 방법으로 '헤더 블록 조각'들로 쪼개져 전송된다.

* 받는 쪽에서는 조각을 다시 붙이고 압축을 해제하여 값을 복원한다.
* 헤더를 압축하고 해제할 때 '압축 컨텍스트'를 사용한다. 오작동하지 않으려면 항상 올바르게 유지해야한다.
* **압축을 해제하는 것이 이 컨텍스트에 영향을 주기때문에 수신측은 어떠한 경우에도 압축을 해제해야한다.**

***

### Server Push

* 서버에서 클라이언트의 요청없이도 리소스를 보낼 수 있게 하는 기능
* 서버에서 클라이언트의 요구를 예측할 수 있을때 유용하다.



CSS, js, html에 들어간 리소스를 서버가 푸시할 수 있음. 이러면 문서를 읽고 요청해야하는 과정이 생략됨.

* 서버는 클라이언트에게 푸시할 것을 알리는 PUSH\_PROMISE 프레임을 전송해야함.
* **서버 푸시를 사용해도, 중간의 프록시가 서버로부터 받은 리소스를 전달하지 않을 수 있음.**
* **서버는 안전하고, 캐싱가능하며, 본문을 포함하지 않는 요청만 푸시한다.**
