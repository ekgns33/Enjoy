# WebSocket 부하테스트 - 터진 서버를 살리자

200명의 동시 사용자 접속에서 에러 발생함.

> 20250124 00:09:23.649 \[lettuce-nioEventLoop-6-3] \[WARN] i.l.c.p.DefaultEndpoint - Unexpected exception during request: java.io.IOException: No buffer space available

* Redis에 사용자의 request마다 업데이트를 치는데 이게 버퍼를 다 사용했다는 에러가 발생.



<figure><img src="../../.gitbook/assets/Screenshot 2025-01-24 at 12.14.27 AM (1).png" alt=""><figcaption></figcaption></figure>

웹소켓 통신을 1분이상 지속하면 Broken pipe가 발생하는 문제가 발생했다.

<mark style="color:red;">**서버에서는 역시 No Buffer Available 에러가 발생했다.**</mark>



#### 원인 분석

사용자는 1초마다 위치 업데이트를 웹소켓으로 전송한다. 기존의 코드에서는 이 위치 업데이트를 서버에서 수신하고 바로 브로드캐스트했다.

```java
public void updateLocation(...) {
	// 위치를 업데이트
	liveLocationService.update(...)

	// 채널로 전송
	simpMessageTemplate.convertAndSend(...)
}
```

요청을 바로 릴레이해버리니 모든 사용자의 위치 업데이트를 서버에서 브로드캐스트해버렸다. 이 과정에서 **네트워크 IO가 과도하게 증가한 것이 장애의 원인**이었다. 여러가지 원인을 예상하고 실제로 확인해 나가며 어떻게 결론을 내렸는지는 다음과 같다.



* **레디스에 너무 많은 요청이 가는걸까?**

초당 400회로 레디스가 죽는다고? 이건 조금 의아했다. 심지어 레디스의 로그를 확인했을때 레디스가 죽은적은 없었다. **커넥션을 담당하는 lettuce가 커넥션이 죽었다가 다시 살아나도 다시 버퍼가 차있다는 에러와 함께 재연결을 반복했다.**

혹시나 **2번의 네트워크 요청을 script를 통한 1회 atomic 요청으로 줄이면** 해결되지 않을까라는 생각에 lua-script를 작성해 요청횟수를 반으로 줄여보았지만 <mark style="color:red;">여전히 문제가 발생했다.</mark>



* **레디스 클라이언트인 lettuce에서 발생했는데 lettuce나 레디스가 문제의 원인 아닐까?**

lettuce도 네티기반의 이벤트 드리븐으로 요청을 처리한다. 200명이 업데이트를 1초에 1번 한다고 했을때 업데이트마다 2회의 요청을 하고있었다. 따라서 추산했을때는 초당 400회의 요청이 레디스로 향하게된다. 반으로 줄인 200회의 요청이라고해도...&#x20;

이게 문제가 아닌것 같았다. 소켓을 확인했을때도 레디스와 스프링서버가 사용하는 커넥션은 1개밖에 없었다. lettuce 풀을 늘려보았기도했지만 문제는 해결되지 않았다. (깃허브의 여러이슈에서 이벤트기반인 레터스에서 풀을 늘리는게 큰의미가 없다는 글을 보기도...)



* **커넥션이 너무 많아서 생긴 문제는 아니었을까?**

에러의 원인을 찾아보면서 너무 많은 소켓을 사용하고 스레드들이 커넥션에 묶여서 생긴 것은 아닐까? 라는 생각을 했다. 하지만 Spring Websocket은 내부적으로 netty를 사용한다. 네티는 이벤트 루프기반의 비동기 웹서버를 구성하게한다. 커넥션마다 스레드를 할당하는게 아니라 Java NIO의 셀렉터를 기반으로 리액터 패턴을 구현해놓았기에 스레드 문제는 아니라고 생각했다.



* **소켓을 너무 많이 열어놓은것은 아닐까?**

**실제로 netstat을 통해 스프링 서버가 부하테스트동안 열고 있는 소켓을 확인할 수 있었다.** 하지만 이게 문제의 원인이라고는 생각하지 않았다. 애초에 **스프링 설정을 통해 최대 소켓 개수, 커넥션 개수를 늘려놓은 상태**였기 때문이다. 에러메세지에서도 버퍼가 가득차서 에러가 발생했다고 알려줬다. dangling 소켓. 즉 열어놓고 사용하지 않는 소켓도 확인했을 때는 없었다.



* **네트워크 IO가 과해서 생긴 문제??**

부하테스트 상황에서 200명의 사용자가 1초마다 위치를 업데이트를 하는경우 서버에서 수신하는 요청은 초당 200개의 메세지를 수신한다. 하지만 서버가 브로드캐스트하는경우 200명의 수신자에게 초당 200개의 메세지를 전달해야한다. **따라서 초당 40000개의 메세지가 네트워크를 통해 전송되는 것이다** :cry:

위에서 발생한 **에러 메세지 역시 소켓으로 네트워크 IO를 하는데 버퍼가 가득 차버렸다는 내용**이었다. IO속도가 매우 빠른 로컬환경에서도 이정도로 버퍼가 찰 수 있나? 를 생각했는데 계산해보니 그럴 수 밖에 없었다.

10명이나 50명일 때는 문제 없던 이유도 여기서 나왔다. 두 경우에는 기존의 로직이어도 초당 100번, 2500번의 네트워크 전달이 발생한다. 그런데 O(n^2) 의 규모로 증가하는 IO 요청으로 발생한 문제라고 생각된다.



* **메세지를 바로 릴레이하지 않고 상태변경 후 중앙에서 그룹으로 전송하자.**

클라이언트가 모바일 기기라는 점에서 네트워크 IO가 과하면, 배터리가 그만큼 많이 소모된다. 또한 굳이 서버에서 즉각적인 갱신을 할 이유도 없었다. **1초마다 화면을 업데이트하는 것이 클라이언트의 구현이기에 스케줄러를 통해 사용자들의 위치를 브로드캐스트하는 것으로 로직을 수정했다.**

```
@Scheduled(...)
public void broadcastLocations() {
	...
}

public void updateLocation(...) {
	// 위치를 업데이트
	liveLocationService.update(...)
}
```
