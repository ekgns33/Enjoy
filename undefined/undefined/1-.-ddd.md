# 1장. DDD 소개

### 1장 DDD 소개

* 도메인 주도 설계는 명확한 커뮤니케이션과 도메인 지식 공유를 위한 디자인 방법론
* 도메인 전문가가 개발 사이클에 들어와서 피드백을 주는 애자일의 한 내용을 소개
  * 번역이 잘못되면 요구사항을 오해하기 쉽다.
* 도메인 전문가, 개발팀, 관계자들이 같은 **모델을 공유하자**
  * 모두가 공유하는 모델을 만드는게 DDD의 목적

모두가 공유하는 인식 모델을 구축하는게 중요한데.. how

* 자료구조보다 비즈니스 이벤트와 작업 흐름에 집중
* 문제 도메인을 하위 도메인으로 자르기
* 각 하위 도메인 별 모델을 만들기
* 공용어 (유비쿼터스언어)를 사용하여 모든 참여자가 이해를 공유하기

#### 1.2 비즈니스 이벤트로 도메인 이해하기

* 비즈니스에서 데이터는 어떤 형태로든 계속 변화한다.
* **비즈니스의 가치는&#x20;**<mark style="color:purple;">**변환 과정**</mark>**에서 창출된다.**
  * 변환이 어떤 연관이 있는지를 이해해야한다.
  * **무엇이 데이터의 변화를 이끌었는지 → 도메인 이벤트**
* 이벤트 스토밍으로 도메인을 탐색
  * 모든 이해 관계자가 참여하여 작업 흐름을 논의
  * 작업 흐름에서 나오는 이벤트들을 정의

{% hint style="warning" %}
보통 기획서, 기획 UI를 보고 서버/클라 개발자가 스펙을 파악하고 서로 질문을 한다. 나중에는 싱크미팅을 잡아서 서로 간의 이해가 맞는지를 합의보는 시간을 갖는데 이건 이벤트 스토밍이라 볼 수 없는걸까?
{% endhint %}



**주문 접수 시스템 예제 (p8)**

* 각 팀에서 어떤 이벤트를 통해서 흐름이 시작되는지를 파악함
* 주문 접수팀에서는 ‘주문서 받음’ 이벤트를 통해 요청을 처리하기 시작한다.
* 주문 접수팀에서 처리를 마친 주문은 ‘접수한 주문’이라고 부른다.
* 배송 팀에서는 ‘주문 접수함’이라는 이벤트로 흐름이 시작된다.



**이벤트를 시간순으로 배치하면 어느팀의 입력이 어느팀의 출력이 되는지 보인다. (p11)**

* 요건 좀 재밌는 것 같다.
* 다음 피처에서 해봐야지
* 시나리오 : 유저 스토리 / 유즈케이스 : 시나리오의 구체화 버전 / 비즈니스 프로세스 : 비즈니스가 달성하려는 목적



**명령을 문서화해라. (p13)**

* 도메인 이벤트가 일어나게 한 것이 바로 **커맨드**다.
* 명령에 따라 작업 흐름이 시작되고 작업흐름이 이벤트를 만들어낸다. 이벤트는 또다른 명령을 발생시킨다.

#### 1.3 도메인을 하위 도메인들로 나누기 **(p15)**

제일 어려운 이야기인 것 같은 챕터.

**커다란 문제를 작은 문제들로 쪼개내는 것은 동일하다.**

* 주문 접수와 관련된 이벤트들을 엮어 낸다.
* 주문 접수 프로세스 내에는 수많은 영역의 작은 팀이 있다.

**DDD에서 도메인이란&#x20;**<mark style="color:purple;">**‘일관된 지식 영역’**</mark>**으로 정의한다.**&#x20;

* 나는 프로그래밍 도메인 전문가?
* 은행원은 은행 창구 도메인 전문가?

**한 도메인 안에서도 구분 지어지는 영역들이 있는데, 이를 하위 도메인이라 부름**

* 큰 도메인 안에서 자체적인 전문 지식을 갖는다.
* 그런데 도메인들끼리 겹치지 않냐? 주문 접수도 배송을 알아야하고 배송도 주문 접수를 알아야하는데?

→ 사실 여기서 아직도 모르겠는게, 개념간 공통부분들은 어디 도메인에 두냐는거다.

→ 모든 영역에서 유저 정보는 쓰이는데? 주문은 배송을 진짜 아예 몰라도 되나?

#### 1.4 바운디드 컨텍스트를 활용 (p17\~p21)

문제 공간, 솔루션 공간을 구분지어야한다.

* **문제 공간은&#x20;**<mark style="color:purple;">**실세계**</mark>
* **솔루션 공간은&#x20;**<mark style="color:purple;">**도메인 모델 세계**</mark>



**문제공간의 도메인, 하위 도메인은 솔루션 공간에서 바운디드 컨텍스트에 대응된다.**

* 각 컨텍스트는 특화된 지식을 표현함.
* 컨텍스트 정보가 없으면 의미가 불분명해짐.



**경계**&#x20;

* **현실에서는 도메인의 경계가 모호하다.**
* 소프트웨어 모델링에서는 서로 독립적일 수록 좋다.
* 의존을 낮추기 위해 노력한다.

{% hint style="danger" %}
**절대 현실의 모든 내용을 모델링에 담아낼 수 없다는 걸 인지하자. (p19)**\
→ 대신 각각의 경계는 명확한 책임이 있어야한다. 각 컨텍스트는 특정 소프트웨어 컴포넌트와 정확히 대응되야하기 때문이다.
{% endhint %}

**HOW?**

* 도메인 전문가의 말에 귀를 기울이기 : 그들이 **동일한 언어를 사용하고 같은 문제에 집중하면 같은 컨텍스트**를 공유하는거다.
* **경계가 늘어나는 것을 주의하자.** 모호한 경계는 경계가 아예 없는 것과 동일하다.
*   작업 흐름이 여려 바운디드 컨텍스트와 상호작용하느라 지연된다면, **디자인을 조금 포기하더라도 작업흐름이 원활하도록 리팩토링하자.**

    * 디자인 보다는 비즈니스 가치가 더 중요하다. 일단 돌아가야지.



**핵심 도메인과 보조 도메인, 일반 도메인을 나누자.**

* 서비스마다 핵심이 되는 도메인이 다르다.
* 별거 아니라고 봤던 영역이 핵심이 될 수도 있다.
* _서로가 생각하기에 중요한 도메인이 다를 수 있다_.

**→ 우선순위를 나누어야한다. 핵심도메인을 먼저 구축하고 거기서부터 확장한다.**

* 레거시에서 도메인을 쪼개기엔 너무 서로 강하게 의존됐다면?

#### 1.5 공용어 만들기 (p21\~p22)

* 코드와 도메인 전문가는 같은 모델을 공유해야한다.
  * 한글과 영어는 다른데 이건 어떻게 해야할까?
  * 개발자는 변수명을 말하는데 기획에서는 한글 용어를 사용한다면?
  * **구체적인 변수명, 클래스명을 언급하는게 아니라 비즈니스 도메인에서 공유하는 정신적 모델**
  * <mark style="color:purple;">**프로젝트 어디에서나 사용하는 언어**</mark>.
* 모든 도메인과 맥락을 포괄하는 공용 언어는 있을 수 없다.
* **각 팀이 용어를 이해하고 바라보는 시선이 다를 수 있다.**
