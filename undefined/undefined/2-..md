# 2장. 도메인 이해하기

### 2장 - 도메인 이해하기

#### 2.1 도메인 전문가 인터뷰하기

* 도메인 전문가는 바쁘다.
* 커맨드 / 이벤트 방식은 작업흐름별로 컨텍스트를 잘라서 짧은 인터뷰를 연이어 할 수 있다.
* 입출력에 집중한다.

{% hint style="warning" %}
→ 도메인을 익힐때 고객의 사용방식을 넘겨짚지 않아야한다.
{% endhint %}

**비기능적 요구사항을 이해하기**

* 고객 대상? B2B? B2C?
* 고객이 뭘 원하는지? 전문가들인지?

**작업 흐름의 나머지 부분 이해하기**

* 인터뷰에서 다른 바운디드 컨텍스트가 등장하면 넘어간다.
* 중요한 정보를 위주로 정의를 명확히한다.

**입력 생각해보기 (p29)**

* ‘주문 알림’ 은 출력인가?
  * 아니다. 고객에게 주문 알림을 보내는 것은 배치 작업 흐름의 부수효과일 뿐이다.
* **작업흐름의 출력은 항상 작업 흐름이 생성한 이벤트로서 다른 바운디드 컨텍스트의 동작을 유발한다.**
  * 작업 흐름의 출력이 ‘주문 접수’ 이벤트가 되어 다른 컨텍스트에 전달된다.
  * 이벤트는 다른 새로운 작업 흐름을 시작한다.

***

#### 2.2 데이터베이스 중심 디자인 지양하기

* 많은 개발 서적서에서 언급하는 내용이다.
* 데이터베이스 중심으로 디자인하면 현실의 도메인을 반영하는데 제약이 생긴다.

**특정 저장소의 구현 방식과 무관하게 도메인을 모델링 하는 것이 좋다.**

* 현실의 도메인을 왜곡하는 현상을 무시해야한다.
* ‘주문’ 과 ‘견적’을 어떻게 모델링 할건가?
  * 플래그로?
  * 비즈니스 규칙 자체가 달라지는데?



***

#### 2.3 클래스 중심의 디자인 지양하기 (p31)

* 의존성 주입같은 객체지향 기법은 DB로부터 영속성 객체를 분리하는 것을 권장한다.
* 객체 관점에서 생각하면 편향될 수 있다.
  * 도메인을 생각하기 전에 이미 클래스 디자인을 생각하고 있을 것이다. → 이거 완전 나구만.
  * **클래스가 디자인을 주도하는 것은 요구사항을 진정으로 듣지 않는다는 것이다.**

***

#### 2.4 도메인 문서화

수집한 요구사항을 어떤 식으로 기록할 수 있을까?

* 작업 흐름은 입력과 출력을 문서화하고 간단한 의사코드로 비즈니스 로직을 표현한다.
* 데이터 구조의 AND는 모두 필요, OR는 둘중 하나.

```java
주문 접수 예시

바운디드 컨텍스트 : 주문 접수

작업 흐름: 주문 접수
  - 트리거 by
		  주문 요청 수신 이벤트
	- 주요 input
		  주문서
	- 다른 input
	    상품 카탈로그
	- 출력 이벤트
	    '주문 접수 완료' 이벤트
	- 사이드 이펙트
	    주문 접수 ACK가 고객에게 전달된다.
```

그러면 데이터 구조를 문서화할 수 있다.

```java
바운디드 컨텍스트 : 주문 접수

data Order = 
  CustomerInfo
  AND ShippingAddress
  AND BillingAddress
  AND list of Orderlines
  AND AmountToBill
  
data OrderLine = 
	Product
	AND Quantity
	AND Price
	
data CustomerInfo = ???
data BillingAddresss = ???
```

* 이런 식으로 데이터에 뭐가 AND, OR인지를 표시한다.
* 데이터베이스 테이블을 만드려고 하는게 아니다. 도메인 그대로를 바라보는 과정.

***

#### 2.5 요구사항 자세히 파악하기 (p33\~ 36)

* **개발자들은 기술적인 문제에 집중하고 모든 요구사항의 온도를 동일하게 취급하는 경향이 있다.**
* 비즈니스에서는 돈을 벌거나 절약하는게 제일 중요하다.
  * 모르겠으면 돈을 아끼는 방향으로, 버는 방향으로 가라.
  * 구현에 들어가는 시간, 리소스도 모두 돈이다.

{% hint style="warning" %}
→ 항상 리소스는 부족하고 순간에 최선의 결정을 내리려고 노력한다. 기술부채는 감수하고 작업할 때도 있다. 그런데 어쩔때는 공수를 더 들여서라도 잘 만들어 놓는게 나중에 큰 나비효과를 방지할 수도 있다. 이런건 진짜 당해봐야 느껴진다.\
\
분명 그때는 이렇게 할 수 밖에 없었는데, 좀 더 리소스를 써서 해놓을걸... (이때부터는 개발이 아니라 예술이 아닌가?)
{% endhint %}



*   카탈로그의 사본이 반드시 필요한가?

    * 개발팀에서 질문 : ‘고객 대응팀이 항상 바로 대응할 수 있어도 사본이 필요한가?’
    * 도메인 전문가 : ‘팀이 바쁘면 방법이 있냐? 전화가 끊기면? 대응팀에 의존 없이 일을 처리하고싶다.’

    → 여기서부터는 의존의 문제다.

**바운디드 컨텍스트의 자율성은 매우 중요하다. (p35)**

* 사본이 필요하다 필요하지 않다와 관계없이 **각 팀은 독립적으로 작업해야한다.**
* 다르게 말하면 이건 너네가 처리해. 이건 내가 처리해?

#### 2.6 복잡미묘한 도메인 모델링하기 (\~p38)

* 질의응답을 통해 많은 정보들을 얻을 수 있다. 이제 이 정보들을 구조화하고 다이어그램으로 표현한다.
* 다이어그램이 모든 것을 반영하지 않을 수 있다.
  * **텍스트 기반 언어로 포착할 수 있을지 확인한다.**

```
바운디드 컨텍스트 : 주문 접수

data widgetCode = string starting with 'W' then 4digits
data GizmoCode = string starting with 'G' then 3digits
data ProductCode = WidgetCode or GizmoCode
```

* 여기서 살펴볼거는 공용어를 사용하는 거다. (위젯코드, 기즈모 코드)
* **디자인에 제약사항을 표시함으로써 디자인 자체로 문서 역할을 해야한다.**
* **요구 사항은 분명히 변하고 우리가 짠 도메인 모델은 매우 쉽게 변경될 것이다.**

```
data OrderQuantity = UnitQuantity or KilogramQuantity

data UnitQuantity = integer between 1 and ?
data KilogramQuantity = decimal between ? and ?
```

* ?에 대해서는 전문가에게 물어본다.
  * 상한이 몇인가요?
  * 제약이 뭔가요?

#### 2.6.2 주문의 생애 주기 표현하기 (p39)

```java
바운디드 컨텍스트 : 주문 접수

data Order = 
  CustomerInfo
  AND ShippingAddress
  AND BillingAddress
  AND list of Orderlines
  AND AmountToBill
  
data OrderLine = 
	Product
	AND Quantity
	AND Price
	
data CustomerInfo = ???
data BillingAddresss = ???
```

* 아까 봤던 주문 도메인 정의다.
* 도메인 전문가에 따르면 **주문에는 생애주기가 있다.**
  * 우편함에서 꺼내면 ‘검증전’
  * ‘검증’
  * ‘가격 책정’
  * **처음에는 가격이 없지만 결국에는 가격이 생긴다.**
* 도메인 전문가에 따르면 각 단계마다 주문서에 표시를 해서 검증 여부를 구분한다.
  * ‘가격 책정이 안된 주문은 배송팀으로 보내져서는 안된다.’ 라는 요구사항
  * 이를 만족시키기 위해 **개별 단계를 도메인에 반영해야한다.**
  * 각 단계를 일컫는 용어를 만든다.

```
data UnvalidatedOrder =
  UnvalidatedCustomerInfo
  AND UnvalidatedShippingAddress
  AND UnvalidatedBillingAddress
  AND list of UnvalidatedOrderLine
  
data UnvalidatedOrderLine = 
  UnvalidatedProductCode
```

* 이 문서는 고객의 정보가 검증되지 않았고 배송지 정보도 검증되지 않음을 명시한다.

```
data ValidatedOrder =
  ValidatedCustomerInfo
  AND ValidatedShippingAddress
  AND ValidatedBillingAddress
  AND list of ValidatedOrderLine
 
data ValidatedOrderLine = 
  ValidatedProductCode
  AND ValidatedOrderQuantity
```

* 검증 후에는 위 모델이 된다.
* 모든 구성요소를 검사했고 유효함을 의미한다.

```
data PricedOrder = 
	ValidatedCustomerInfo
	AND ValidatedShippingAddress
	AND ValidatedBillingAddresss
	AND list of PricedOrderLine // 새로운 정보 등장
  AND AmountToBill
  
data PricedOrderLine = 
	ValidatedOrderLine
	AND AcknowledgmentLetter
	
	
data PlacedOrderAcknowledgment = 
  PricedOrder
  AND AckowledgmentLetter
```

* 지금까지 작성한 내용으로 포착할 수 있는 내용들이 생긴다.
  * 검증하지 않은 주문은 가격이 없다.
  * 검증한 주문은 모든 주문 라인을 검증해야한다.

복잡할 수 있지만 비즈니스 로직을 모두 녹여냈다. → 이걸 **코드로 녹여내면 도메인 주도 디자인이된다.**

{% hint style="warning" %}
→ 보통 디자인을 할때 머리속으로 상태에 대한 변경, 전파를 떠올린다.

→ 다음 피처할때는 요걸 한번 그려볼까
{% endhint %}

#### 2.6.3 작업 흐름의 단계 구체화하기 (p41\~)

**전체 작업흐름을 먼저 구상했다면 각 단계를 입력과 출력으로 나눠보자.**

* 각 단계를 나누고 의사코드로 문서화한다.
* 흐름에 대한 문서화 이후에는 각 하위 단계에 대한 세부 정보를 추가한다.
* 이렇게 작성한 문서는 기술이 들어있지 않다. 도메인 전문가가 읽고도 확인 가능하다.

{% hint style="warning" %}
→ 테크 스펙을 작성할때 복잡한 부분은 의사코드를 작성하거나 다이어그램을 그린다.

→ 하지만 이것 역시 개발자를 위한 문서라서 도메인 문서라고 할 수 없을 것 같다.
{% endhint %}
