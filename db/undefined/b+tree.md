# 인덱스와 B+Tree

## B+ Tree

**다분기 트리**

* 분기 개수가 여러개임. 분기 개수가 많아지면 계층의 높이는 낮아짐.
* 따라서 액세스 횟수가 적어진다.

### 인덱스에 B+ 트리를 쓰는 이유

B+ 트리 인덱스는 **어떤 검색이어도 루트에서 리프까지 가지 않으면 검색할 수 없는 단점**이 있음.\
하지만 **브랜치가 컴팩트하게되어 인덱스의 계층구조 자체를 줄여버림. 최악의 경우의 액세스 횟수를 줄이게됨.**

광범위 검색의 경우 액세스가 완결되지 않는 경우가 있음.\
B+트리 인덱스는 주변의 리프블록으로 넘어가 원하는 결과를 얻어냄.

*   B+트리는 리프노드들이 Sequential하게 연결되어 있음. 따라서 순차 처리가 단순 연결리스트를 순회하는 것임.

    따라서 순차처리 시에 효율적이다.
* 하지만 B트리는 순회하려면 브랜치로 돌아가서 중위 순회 탐색을 해야함.

### 인덱스의 사용

#### 멀티 컬럼 인덱스

* 인덱스 검색을 하는데 지정하는 조건이 여러개가 있을때, ID만 인덱스로 찾는것보다 조건까지 인덱스로 엮는게 더 좋을 수 있음.

#### 커버링 인덱스

* 인덱스 검색에서는 인덱스를 읽고 인덱스가 가리키는 데이터영역을 찾아가서 읽는 절차를 사용함.



**인덱스 부분과 데이터 부분이 서로 독립적인 영역에 존재**하기에 양쪽을 한번의 액세스로 읽을 수는 없음.

근데 검색하는 패턴이 전체 엔티티를 조회하는게 아니라 딱 **인덱스를 거는 값만 필요로한다면**, 실제 데이터에 접근하지 않고 인덱스만보고 처리할 수 있음. **따라서 실제 위치를 찾아가는 랜덤 액세스를 줄일 수 있음.**

#### 인덱스 병합

* 데이터를 검색할때, 조건이 여러개일 수 있음.
* OR조건 검색을 할때 하나의 인덱스만은 도움이 안될 수 있음.



**한 번의 검색에서 두 개 이상의 인덱스를 동시에 사용**하여 각각의 결과에서 원하는 레코드를 꺼내는 방법

1. 각 인덱스에서 각각 검색을 실시하여 행 번호 추출
2. AND, OR 집합 연산을 수행
3. 결과에 대해서 실제 데이터를 읽는다.

#### 결국 랜덤 액세스가 문제임.

* 데이터베이스에서는 갱신한 데이터를 결국 디스크에 적어야함. 보통 메모리보다 더 많은 데이터를 저장하기에, 디스크에 쓰고 읽는 것이 발생할 수 밖에 없음. 대부분 이런 경우 랜덤 액세스임.
* 디스크는 진짜 느림. 아무리 좋아도 초당 수백회전수임. 따라서 랜덤액세스요청이 많이 들어오면 버틸 수 없을 지도 모른다.

#### 인덱스 업데이트도 비용이다.

인덱스는 실제 데이터와 별개로 저장하기에 **데이터의 업데이트가 생기면 인덱스도 업데이트를 해야한다.**\
따라서 업데이트 성능이 떨어진다. 상용 데이터베이스는 몇가지 방법을 사용한다.



1. **디스크에 모아서 기록하기**

* 레코드를 추가 등록할때는 B+인덱스에도 등록해야함. 여기 저기 인덱스의 리프 블록에 업데이트가 무작위로 발생함.
* DB는 업데이트 된 부분(블록)을 최대한 빨리 디스크에 저장해야함. 그런데 업데이트 순서대로 적으면 랜덤 액세스가 많아짐. 따라서 버퍼에 잠시 기록하고 모아서 한번에 리프 블록을 갱신하는 구조를 사용함.

&#x20;       MySQL의 InnoDB가 해당 방식을 적음. 랜덤 쓰기보다는 시퀀셜하게 적어서 빠르게 적음.



2. **병렬 갱신 성능 향상**

* B+트리 인덱스에 값의 추가/갱신/삭제를 하면 인덱스의 리프 블록 내용을 이동시킬 수 있음.
* 리프 분할이라고함.
* 업데이트를 동시에 많이 수행하면 리프분할이 여기저기서 발생함. 이때 일관성 지키기가 어려움. MySQL은 인덱스 재편성이 될때 까지 참조/갱신을 막는 동작을함.
* MySQL에서는 파티션 테이블을 사용함. 파티션 테이블은 사용자에게는 테이블이 하나로 보이는데 실제로는 복수로 분할관리함. 인덱스도 분할 관리하기때문에 병렬로 처리가 가능해짐. :thinking:

#### 배운점

* 인덱스로만 데이터를 조회하는 방법도 있다. (커버링 인덱스)
* 데이터베이스는 결국 File에 데이터를 저장하기에 어떻게든 Random Access를 줄이려한다.
  * 모든 소프트웨어가 그렇지만 디비는 Storage와 연관이 깊은 소프트웨어이기에 더 민감하다.
